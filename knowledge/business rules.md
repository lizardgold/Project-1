## Назначение документа

Документ содержит бизнес-правила и ограничения, применяемые при анализе и проектировании сервиса "ПодписьОнлайн".

Правила используются как основа для подготовки системно-аналитических артефактов, включая:

- OpenAPI-спецификации;
- Sequence-диаграммы;
- спецификации ошибок, повторных запросов и интеграционного взаимодействия.

## User Stories

### Подписание пакета документов

**US-01. Формирование и отправка пакета документов**
- Как сотрудник партнёра, я хочу сформировать пакет из нескольких документов и отправить его клиенту на подписание, чтобы клиент мог подписать все необходимые документы в рамках одного процесса.

**US-02. Просмотр пакета документов**
- Как клиент, я хочу просмотреть все документы, входящие в пакет, до подписания, чтобы понимать содержание и условия каждого документа.

**US-03. Подписание пакета документов**
- Как клиент, я хочу подписать пакет документов с помощью усиленной квалифицированной электронной подписи (УКЭП) в мобильном приложении партнёра, чтобы не использовать физический токен и компьютер.

**US-04. Частичное подписание пакета**
- Как система, я хочу отслеживать состояние подписания каждого документа отдельно, чтобы корректно определять общий статус пакета и не считать пакет подписанным до завершения подписания всех обязательных документов.

**US-05. Отказ от подписания**
- Как клиент, я хочу иметь возможность отказаться от подписания пакета, чтобы не подтверждать документы, с условиями которых я не согласен.

### Выпуск и отзыв сертификата

**US-06. Выпуск сертификата**
- Как клиент, я хочу получить сертификат квалифицированной электронной подписи после успешной проверки личности, чтобы подписывать документы непосредственно с телефона.

**US-07. Просмотр информации о сертификате**
- Как клиент, я хочу видеть информацию о действующем сертификате и его состоянии, чтобы понимать, могу ли я использовать его для подписания документов.

**US-08. Инициация отзыва сертификата**
- Как клиент, я хочу инициировать отзыв сертификата при потере телефона или подозрении на компрометацию ключа, чтобы исключить возможность дальнейшего использования скомпрометированной электронной подписи.

**US-09. Контроль результата отзыва**
- Как клиент, я хочу получить информацию о результате отзыва сертификата, чтобы понимать, прекращена ли возможность использования сертификата для подписания.

## Жизненные циклы сущностей

### Документ
Документ - это сущность, содержащая данные, подлежащие подписанию клиентом.

#### Перечень статусов

| Статус                 | Код                   | Описание                                                        |
| ---------------------- | --------------------- | --------------------------------------------------------------- |
| Получен                | `RECEIVED`            | Документ получен от партнёра.                                   |
| На проверке            | `VALIDATING`          | Выполняется проверка структуры, формата и метаданных документа. |
| Готов к подписанию     | `READY_FOR_SIGNATURE` | Проверки завершены успешно, документ готов к подписанию.        |
| Ожидает подписания     | `PENDING_SIGNATURE`   | Документ доступен клиенту для подписания.                       |
| Подписание выполняется | `SIGNING`             | Выполняется криптографическая операция подписания.              |
| Подписан               | `SIGNED`              | Подпись успешно сформирована и сохранена.                       |
| Отклонён               | `REJECTED`            | Клиент отказался от подписания документа.                       |
| Истёк                  | `EXPIRED`             | Истёк срок подписания документа.                                |
| Отменён                | `CANCELLED`           | Документ отменён партнёром до завершения подписания.            |
| Ошибка проверки        | `VALIDATION_FAILED`   | Документ не прошёл проверку.                                    |
| Ошибка подписания      | `SIGNING_FAILED`      | Операция подписания завершилась ошибкой.                        |
#### Переходы между статусами

| Исходный статус       | Целевой статус        | Событие / условие перехода                                       |
| --------------------- | --------------------- | ---------------------------------------------------------------- |
| `RECEIVED`            | `VALIDATING`          | Документ передан на проверку.                                    |
| `VALIDATING`          | `READY_FOR_SIGNATURE` | Все проверки завершились успешно.                                |
| `VALIDATING`          | `VALIDATION_FAILED`   | Обнаружены ошибки формата, структуры или обязательных атрибутов. |
| `READY_FOR_SIGNATURE` | `PENDING_SIGNATURE`   | Документ включён в отправленный клиенту пакет.                   |
| `PENDING_SIGNATURE`   | `SIGNING`             | Клиент подтвердил подписание.                                    |
| `SIGNING`             | `SIGNED`              | Криптографическая операция завершилась успешно.                  |
| `SIGNING`             | `SIGNING_FAILED`      | Криптографическая операция завершилась неуспешно.                |
| `SIGNING_FAILED`      | `SIGNING`             | Повторная попытка подписания разрешена и инициирована.           |
| `PENDING_SIGNATURE`   | `REJECTED`            | Клиент отказался от подписания документа.                        |
| `PENDING_SIGNATURE`   | `EXPIRED`             | Истёк срок подписания.                                           |
| `PENDING_SIGNATURE`   | `CANCELLED`           | Партнёр отменил документ до начала подписания.                   |
#### Правила переходов

**DOC-01. Проверка документа**
До передачи документа клиенту система должна проверить:
- наличие обязательных метаданных;
- допустимость формата файла;
- соответствие установленным ограничениям размера;
- целостность полученного файла;
- наличие идентификатора документа;
- возможность обработки документа механизмом подписания.

**DOC-02. Неизменность оригинала**
Система должна сохранять исходное содержимое документа. Подписание должно выполняться относительно конкретной версии документа.

**BR-DOC-03. Контроль целостности**
Перед подписанием система должна вычислить или проверить криптографический хеш документа. Подпись должна относиться именно к той версии содержимого, которую клиент подтвердил.

**BR-DOC-04. Успешное подписание**
Документ получает статус `SIGNED` только после успешного завершения криптографической операции и сохранения результата подписания.

**BR-DOC-05. Ошибка подписания**

В случае временной технической ошибки операция может быть повторена при условии, что исключено создание дублирующего результата подписания.

**BR-DOC-06. Подписанный документ**
После получения статуса `SIGNED` изменение содержимого документа запрещено. Любое изменение должно приводить к созданию новой версии или нового документа и повторному подписанию.

**BR-DOC-07. Проверка электронной подписи**
Система должна предоставлять возможность проверить:
- целостность подписанного документа;
- соответствие подписи подписанному содержимому;
- сертификат, которым выполнено подписание;
- срок действия сертификата на момент подписания;
- статус сертификата с учётом времени подписания и доступных сведений об отзыве.

**BR-DOC-08. Разделение результата подписания и его проверки**
Успешное формирование подписи и последующая проверка её действительности являются разными операциями. Ошибка проверки не должна автоматически изменять сохранённый факт выполнения криптографической операции.

### Пакет документов
Пакет документов - это сущность, объединяющая один или несколько документов, которые направляются клиенту для ознакомления и подписания в рамках единого процесса.

#### Перечень статусов

|Статус|Код|Описание|
|---|---|---|
|Черновик|`DRAFT`|Пакет создан, но ещё не отправлен клиенту.|
|На проверке|`VALIDATING`|Выполняется проверка состава, содержимого и метаданных документов.|
|Ожидает подписания|`PENDING_SIGNATURE`|Проверки завершены, пакет доступен клиенту для подписания.|
|В процессе подписания|`IN_PROGRESS`|Клиент начал процесс подписания, но ещё не завершил его.|
|Частично подписан|`PARTIALLY_SIGNED`|Часть обязательных документов подписана, остальные ожидают подписания.|
|Подписан|`SIGNED`|Все обязательные документы успешно подписаны.|
|Отклонён|`REJECTED`|Клиент отказался от подписания пакета.|
|Истёк|`EXPIRED`|Истёк срок, отведённый на подписание пакета.|
|Отменён|`CANCELLED`|Пакет отменён партнёром до завершения подписания.|
|Ошибка обработки|`FAILED`|Произошла критическая ошибка, препятствующая дальнейшей обработке пакета.|

#### Переходы между статусами

|Исходный статус|Целевой статус|Событие / условие перехода|
|---|---|---|
|`DRAFT`|`VALIDATING`|Партнёр отправил пакет на обработку.|
|`VALIDATING`|`PENDING_SIGNATURE`|Все документы прошли проверки.|
|`VALIDATING`|`FAILED`|Обнаружена критическая ошибка обработки.|
|`PENDING_SIGNATURE`|`IN_PROGRESS`|Клиент начал процесс подписания.|
|`PENDING_SIGNATURE`|`PARTIALLY_SIGNED`|Первый документ подписан, остальные ещё ожидают подписания.|
|`IN_PROGRESS`|`PARTIALLY_SIGNED`|Подписана только часть обязательных документов.|
|`IN_PROGRESS`|`SIGNED`|Все обязательные документы подписаны.|
|`PARTIALLY_SIGNED`|`SIGNED`|Подписаны все оставшиеся обязательные документы.|
|`PENDING_SIGNATURE`|`REJECTED`|Клиент отказался от подписания.|
|`IN_PROGRESS`|`REJECTED`|Клиент отказался от дальнейшего подписания.|
|`PARTIALLY_SIGNED`|`REJECTED`|Клиент отказался от подписания оставшихся документов.|
|`PENDING_SIGNATURE`|`EXPIRED`|Истёк срок подписания.|
|`IN_PROGRESS`|`EXPIRED`|Истёк срок подписания.|
|`PARTIALLY_SIGNED`|`EXPIRED`|Истёк срок подписания оставшихся документов.|
|`DRAFT`|`CANCELLED`|Партнёр отменил черновик.|
|`PENDING_SIGNATURE`|`CANCELLED`|Партнёр отменил отправленный пакет до начала подписания.|
#### Правила переходов

**PKG-01. Неизменность отправленного пакета**
После перехода в `PENDING_SIGNATURE` состав пакета и содержимое входящих документов не могут изменяться.

**PKG-02. Условие завершения**
Пакет считается подписанным только при успешном подписании всех документов, для которых установлено требование обязательного подписания.

**PKG-03. Независимость статусов**
Изменение статуса отдельного документа должно инициировать пересчёт статуса пакета. Статус пакета не должен изменяться независимо от фактического состояния входящих документов, кроме специальных событий: отказ, истечение срока и отмена.

**PKG-04. Неизменность подписанных документов**
После подписания документа его содержимое не может быть изменено. Для изменения содержания необходимо сформировать новый документ и новый процесс подписания.

**PKG-05. Отмена пакета**
Отмена пакета не отменяет и не аннулирует ранее созданные электронные подписи. Подписанные документы сохраняют юридически значимый результат подписания.

**PKG-06. Терминальные статусы**
К терминальным статусам пакета относятся:
- `SIGNED`;
- `REJECTED`;
- `EXPIRED`;
- `CANCELLED`;
- `FAILED`.

Из терминальных статусов переходы в другие состояния запрещены. Для повторного процесса необходимо создать новый пакет.

**PKG-07. Срок действия**
Для пакета должен задаваться срок, до которого клиент может выполнить подписание. По истечении срока система должна автоматически инициировать переход в `EXPIRED`, если пакет не завершён.

### Сертификат

Сертификат - это электронный документ, выпускаемый удостоверяющим центром и связывающий открытый ключ проверки электронной подписи с определённым владельцем.

#### Перечень статусов

|Статус|Код|Описание|
|---|---|---|
|Запрошен|`REQUESTED`|Клиент инициировал процедуру выпуска сертификата.|
|На проверке|`PENDING_VERIFICATION`|Выполняется проверка личности и необходимых сведений клиента.|
|Ожидает выпуска|`PENDING_ISSUANCE`|Проверки пройдены, запрос передан в удостоверяющий центр.|
|Активен|`ACTIVE`|Сертификат выпущен, действует и может использоваться для подписания.|
|Приостановлен|`SUSPENDED`|Использование сертификата временно запрещено.|
|Отозван|`REVOKED`|Удостоверяющий центр подтвердил отзыв сертификата.|
|Истёк|`EXPIRED`|Завершился срок действия сертификата.|
|Отказано в выпуске|`REJECTED`|Удостоверяющий центр или проверяющая система отказали в выпуске.|
|Ошибка выпуска|`ISSUANCE_FAILED`|Произошла техническая ошибка при выпуске сертификата.|
#### Переходы между статусами

|Исходный статус|Целевой статус|Событие / условие перехода|
|---|---|---|
|`REQUESTED`|`PENDING_VERIFICATION`|Инициирована проверка личности.|
|`PENDING_VERIFICATION`|`PENDING_ISSUANCE`|Проверка личности завершилась успешно.|
|`PENDING_VERIFICATION`|`REJECTED`|Проверка личности завершилась отказом.|
|`PENDING_ISSUANCE`|`ACTIVE`|Удостоверяющий центр выпустил сертификат.|
|`PENDING_ISSUANCE`|`REJECTED`|Удостоверяющий центр отказал в выпуске.|
|`PENDING_ISSUANCE`|`ISSUANCE_FAILED`|Произошла техническая ошибка выпуска.|
|`ISSUANCE_FAILED`|`PENDING_ISSUANCE`|Повторная попытка выпуска разрешена.|
|`ACTIVE`|`SUSPENDED`|Сертификат временно приостановлен.|
|`SUSPENDED`|`ACTIVE`|Приостановление снято, сертификат снова разрешён к использованию.|
|`ACTIVE`|`REVOKED`|Удостоверяющий центр подтвердил отзыв.|
|`SUSPENDED`|`REVOKED`|Удостоверяющий центр подтвердил отзыв.|
|`ACTIVE`|`EXPIRED`|Наступила дата окончания срока действия.|
|`SUSPENDED`|`EXPIRED`|Наступила дата окончания срока действия.|

#### Правила работы сертификата

**CERT-01. Уникальность сертификата**
Каждый выпущенный сертификат должен иметь уникальный серийный номер в рамках соответствующего удостоверяющего центра.

**CERT-02. Связь с владельцем**
Сертификат должен быть связан с идентифицированным клиентом. Система должна проверять соответствие владельца сертификата пользователю, инициирующему подписание.

**CERT-03. Условия использования**
Для выполнения нового подписания сертификат должен:
- иметь статус `ACTIVE`;
- находиться в пределах срока действия;
- не иметь подтверждённого отзыва;
- соответствовать требованиям к квалифицированной электронной подписи;
- быть доступен механизму подписания.

**CERT-04. Приостановление**
При статусе `SUSPENDED` использование сертификата для новых операций подписания запрещено.

Поддержка приостановления зависит от возможностей удостоверяющего центра и применимого законодательства. Если УЦ не поддерживает данную операцию, статус исключается из фактической реализации.

**CERT-05. Отзыв**
Отзыв сертификата является необратимой операцией. После подтверждения отзыва сертификат не может быть повторно активирован.

**CERT-06. Истечение срока действия**
Сертификат автоматически переходит в `EXPIRED` при наступлении даты окончания срока действия, если он не был отозван ранее.

**CERT-07. Историческая проверка**
Отзыв или истечение срока действия сертификата не должны автоматически приводить к признанию недействительными всех подписей, сформированных ранее.

Для проверки подписи необходимо учитывать:
- время подписания;
- срок действия сертификата;
- сведения об отзыве на соответствующий момент;
- наличие доверенной метки времени, если она предусмотрена используемой схемой;
- требования применимого законодательства и криптографического профиля.

**CERT-08. Разделение сертификата и ключевой пары**
Сертификат и закрытый ключ являются разными сущностями. Сертификат содержит открытый ключ и сведения о владельце, а закрытый ключ используется для создания подписи.

Закрытый ключ не должен передаваться партнёру или сохраняться в открытом виде в информационных системах, не предназначенных для его защищённого хранения и использования.

### Операции отзыва сертификата

Операция отзыва - это самостоятельная сущность, представляющая запрос на отзыв сертификата и отслеживающая результат взаимодействия с удостоверяющим центром.

**Важно!** Операция отзыва и сертификат имеют разные жизненные циклы.

Например, операция может находиться в статусе `PROCESSING`, в то время как сертификат продолжает иметь статус `ACTIVE`. Это означает, что запрос на отзыв отправлен, но удостоверяющий центр ещё не подтвердил результат.

#### Перечень статусов

|Статус|Код|Описание|
|---|---|---|
|Создана|`CREATED`|Операция отзыва зарегистрирована системой.|
|Ожидает подтверждения|`PENDING_CONFIRMATION`|Требуется дополнительное подтверждение клиента.|
|Ожидает отправки|`PENDING_SUBMISSION`|Операция подготовлена к передаче в удостоверяющий центр.|
|Отправлена|`SUBMITTED`|Запрос передан в удостоверяющий центр.|
|Обрабатывается|`PROCESSING`|Удостоверяющий центр обрабатывает запрос.|
|Успешно завершена|`SUCCEEDED`|Отзыв подтверждён удостоверяющим центром.|
|Ошибка обработки|`FAILED_RETRYABLE`|Произошла временная ошибка, допускающая повторную попытку.|
|Окончательная ошибка|`FAILED_FINAL`|Операция завершилась ошибкой, повторная попытка невозможна без изменения исходных данных или отдельного решения.|
|Отменена|`CANCELLED`|Операция отменена до её принятия удостоверяющим центром.|
#### Переходы между статусами операции отзыва

|Исходный статус|Целевой статус|Событие / условие перехода|
|---|---|---|
|`CREATED`|`PENDING_CONFIRMATION`|Система требует дополнительного подтверждения клиента.|
|`CREATED`|`PENDING_SUBMISSION`|Все необходимые проверки и подтверждения пройдены.|
|`PENDING_CONFIRMATION`|`PENDING_SUBMISSION`|Клиент подтвердил отзыв.|
|`PENDING_CONFIRMATION`|`CANCELLED`|Клиент отказался от выполнения операции.|
|`PENDING_SUBMISSION`|`SUBMITTED`|Запрос успешно передан в удостоверяющий центр.|
|`SUBMITTED`|`PROCESSING`|Удостоверяющий центр принял запрос в обработку.|
|`SUBMITTED`|`SUCCEEDED`|Удостоверяющий центр сразу вернул подтверждение отзыва.|
|`SUBMITTED`|`FAILED_RETRYABLE`|Возникла временная техническая ошибка.|
|`SUBMITTED`|`FAILED_FINAL`|Получен окончательный отказ в выполнении операции.|

|`FAILED_RETRYABLE`|`PENDING_SUBMISSION`|Разрешена повторная отправка запроса.|
|`CREATED`|`CANCELLED`|Операция отменена до отправки запроса.|
|`PENDING_SUBMISSION`|`CANCELLED`|Операция отменена до отправки запроса.|

#### Правила работы

**REV-01. Уникальность операции**
Каждая операция отзыва должна иметь уникальный идентификатор.

**REV-02. Основание отзыва**
При создании операции должно фиксироваться основание отзыва, например:
- потеря мобильного устройства;
- подозрение на компрометацию закрытого ключа;
- утрата контроля над устройством;
- инициатива владельца сертификата;
- иное предусмотренное основание.

**REV-03. Подтверждение операции**
Перед отправкой запроса в удостоверяющий центр система должна проверить наличие необходимых полномочий и подтверждения личности инициатора.

**REV-04. Асинхронная обработка**
Отзыв сертификата может выполняться асинхронно. Отправка запроса в удостоверяющий центр не означает, что сертификат уже отозван.

**REV-05. Подтверждение результата**
Операция получает статус `SUCCEEDED` только после получения достоверного подтверждения от удостоверяющего центра.

**REV-06. Запрет повторной активации**
После успешного отзыва сертификат не может быть возвращён в статус `ACTIVE`. Для дальнейшего использования УКЭП необходимо пройти процедуру выпуска нового сертификата.

**REV-07. Идемпотентность**
Повторная отправка одного запроса на отзыв не должна приводить к созданию нескольких независимых операций отзыва одного сертификата с одинаковым основанием и контекстом.

**REV-08. Неопределённый результат**
Если соединение с удостоверяющим центром было прервано после отправки запроса, система не должна автоматически считать операцию неуспешной.

Необходимо сначала запросить актуальное состояние сертификата или операции у удостоверяющего центра, чтобы исключить повторное выполнение уже завершённого отзыва.

**REV-09. Аудит**
Для каждой операции необходимо сохранять:
- идентификатор сертификата;
- идентификатор инициатора;
- дату и время создания;
- основание отзыва;
- историю изменения статусов;
- идентификатор запроса во внешней системе;
- результат обработки удостоверяющим центром;
- сведения об ошибках и повторных попытках.

**REV-10. Запрет использования после подтверждённого отзыва**
После получения подтверждения отзыва система должна запрещать использование сертификата для новых операций подписания.

**Правило:** Сервис "ПодписьОнлайн" предназначен для подписания документов клиентом с использованием мобильного телефона в приложении банка или страховой организации.

- Конкретные способы аутентификации, подтверждения действий и взаимодействия с криптографическими средствами определяются отдельно.

**1.2. Приём документов от партнёра**
**Правило:** Сервис принимает документы для подписания от систем партнёров.
**Следствия:**
- Взаимодействие с партнёром должно быть отражено в системных контрактах и интеграционных сценариях.

- Неизвестные параметры интеграции не должны выдаваться за подтверждённые ограничения.

**1.3. Выпуск сертификата после проверки личности**
**Правило:** Выпуск сертификата электронной подписи для клиента выполняется после проверки его личности.
**Следствия:**
- Выпуск сертификата должен быть связан с результатом проверки личности.
- Сценарий выпуска сертификата должен учитывать невозможность продолжения при отрицательном результате проверки.

**1.4. Подписание с подтверждением клиента**
**Правило:** Подписание документа выполняется с подтверждением клиента.
**Следствия:**
- Система должна различать подготовку операции подписания и подтверждённое намерение клиента выполнить подписание.
- Подтверждение клиента не должно подменяться фактом получения документа от партнёра.
- Конкретный механизм подтверждения и его связь с отдельными документами или пакетом документов определяются в соответствующем сценарии.

**1.5. Хранение подписанных документов**
**Правило:** Сервис обеспечивает хранение подписанных документов.
**Следствия:**
- Должна быть предусмотрена возможность определить результат подписания и получить подписанный документ в рамках разрешённого сценария доступа.
- Требования к срокам хранения, размещению, доступу, архивированию и удалению определяются отдельно.
- Хранение документа не должно само по себе считаться доказательством корректности электронной подписи.

**1.6. Проверка электронной подписи**
**Правило:** Сервис предусматривает возможность проверки электронной подписи.
**Следствия:**

- Критерии успешной проверки и состав проверяемых атрибутов должны определяться соответствующими требованиями.

**1.7. Использование внешних систем**
**Правило:** В процессе работы сервис взаимодействует с внешними системами, включая удостоверяющий центр, Госуслуги (ЕСИА) и системы партнёров.
**Следствия:**
- Внешние интеграции должны учитываться при моделировании сценариев и системных взаимодействий.

## 2. Бизнес-правила подписания пакета документов

**2.1. Поддержка пакетного подписания**
**Правило:** Сервис должен поддерживать сценарий подписания нескольких документов в рамках одной пользовательской операции.
**Следствия:**
- Должна быть предусмотрена возможность определить состав пакета.
- Артефакты должны различать пакет документов и входящие в него отдельные документы.
- Пакетное взаимодействие не означает, что все документы обязательно обрабатываются как единая неделимая сущность на техническом уровне.

**2.2. Различение результата пакета и результатов документов**
**Правило:** Результат обработки пакета должен позволять определить результат обработки каждого входящего документа.
**Следствия:**
- Агрегированный статус пакета не должен скрывать существенные различия между результатами отдельных документов.
- Если пакет обработан не полностью, система должна предоставлять достаточно информации для определения завершённых и незавершённых частей операции.
- Конкретный набор статусов определяется в модели состояний и соответствующих контрактах.

**2.3. Подтверждение намерения подписать пакет**
**Правило:** До выполнения подписания система должна учитывать подтверждённое намерение клиента подписать документы.
**Следствия:**
- Получение пакета от партнёра само по себе не является согласием клиента на подписание.
- Механизм подтверждения должен быть определён в пользовательском сценарии.
- Возможность единого подтверждения для всего пакета или отдельных подтверждений для документов не считается окончательно установленной без дополнительного решения.

**2.4. Сохранение результатов отдельных подписаний**
**Правило:** Ошибка обработки одного документа не должна автоматически трактоваться как отмена результатов подписания остальных документов.
**Следствия:**
- Система должна учитывать возможность частичного выполнения пакетной операции.
- В диаграммах необходимо показывать обработку частичных результатов, если она применима к выбранной модели выполнения.
- Автоматическая компенсация уже выполненных криптографических операций не предполагается без отдельного обоснования и подтверждённого механизма.

## 3. Бизнес-правила отзыва сертификата

**3.1. Отзыв сертификата при потере телефона**
**Правило:** Сервис должен поддерживать сценарий отзыва сертификата при потере телефона клиента.
**Следствия:**
- Сценарий должен учитывать риск несанкционированного использования сертификата.
- Необходимо предусмотреть возможность инициировать отзыв и определить результат обработки запроса.
- Конкретный способ идентификации клиента при отсутствии доступа к потерянному устройству должен быть определён отдельно.

**3.2. Отзыв как отдельная операция**
**Правило:** Запрос на отзыв сертификата рассматривается как отдельная операция с собственным идентификатором и результатом обработки.
**Следствия:**
- Операция отзыва должна быть связана с конкретным сертификатом.
- Должна быть возможность определить состояние и результат операции независимо от результата её первоначального запроса.
- Повторные запросы должны обрабатываться с учётом уже существующей операции, если они относятся к одному и тому же намерению отзыва.

**3.3. Различение принятия запроса и фактического отзыва**
**Правило:** Принятие запроса на отзыв не означает, что сертификат уже фактически отозван.
**Следствия:**
- Система должна различать приём запроса, выполнение операции и подтверждённый результат отзыва.
- Ответ об успешном приёме запроса не должен интерпретироваться как подтверждение завершённого отзыва.
- Финальный результат должен основываться на доступных подтверждениях от системы, ответственной за отзыв сертификата.

**3.4. Повторный отзыв сертификата**
**Правило:** Повторный запрос на отзыв должен обрабатываться с учётом актуального состояния сертификата и результата предыдущих попыток.
**Следствия:**
- Повторный запрос не должен без необходимости приводить к неконтролируемому повторению операции.
- При неопределённом результате предыдущей попытки следует использовать доступный механизм проверки актуального состояния сертификата.
- Поведение при уже отозванном сертификате должно быть определено в контракте как отдельный ожидаемый результат или согласованный вариант успешной обработки.

## 4. Правила обработки операций и ошибок

**4.1. Различение сущностей**
**Правило:** Документ, пакет документов, бизнес-операция и сертификат являются различными сущностями и не должны использоваться как взаимозаменяемые понятия.
**Следствия:**
- Каждый объект должен иметь собственное назначение в модели данных.
- Связи между объектами должны отражаться явно.
- Статус пакета не заменяет статусы отдельных документов, а статус операции не заменяет состояние сертификата.

**4.2. Идентификация объектов и операций**
**Правило:** Для объектов и операций, состояние которых необходимо отслеживать, должны предусматриваться идентификаторы.
**Следствия:**
- Контракты должны позволять однозначно связать запрос, операцию и её результат.
- Идентификаторы должны использоваться последовательно в API, моделях данных и диаграммах.
- Формат, область уникальности и правила генерации идентификаторов определяются отдельно.

**4.3. Различение бизнес-ошибок и технических ошибок**
**Правило:** Бизнес-ошибки и технические ошибки должны различаться в контрактах и сценариях обработки.
**Следствия:**
- Для ошибок, связанных с бизнес-условиями, и ошибок инфраструктуры должны быть предусмотрены различимые результаты.
- Возможность повторного запроса должна зависеть от характера ошибки.
- Ошибка не должна считаться окончательной только на основании того, что запрос завершился с технической ошибкой.

**4.4. Неопределённый результат операции**
**Правило:** Отсутствие ответа от системы не является доказательством ни успешного, ни неуспешного выполнения операции.
**Следствия:**
- Система должна различать подтверждённый результат и ситуацию, в которой результат пока неизвестен.
- При необходимости должен быть предусмотрен способ получить актуальное состояние операции.
- Нельзя автоматически сообщать клиенту об успешном выполнении, если оно не подтверждено.
- Нельзя автоматически повторять потенциально необратимую операцию, не оценив вероятность того, что предыдущий запрос уже был обработан.

**4.5. Идемпотентность и повторная доставка**
**Правило:** Повторная доставка одного и того же запроса не должна приводить к неконтролируемому дублированию бизнес-операции.
**Следствия:**
- Для операций, допускающих повторную отправку, необходимо определить механизм распознавания повторов.
- Правила идемпотентности должны быть описаны в API-контрактах или связанных спецификациях.
- Следует различать повтор того же запроса и новую самостоятельную операцию.
- Конкретный механизм, область действия ключа идемпотентности и срок его хранения определяются отдельно.

**4.6. Контролируемые повторные попытки**
**Правило:** Повторные попытки допустимы только при соблюдении определённых условий безопасности и с учётом характера ошибки.
**Следствия:**
- Временные ошибки следует отличать от ошибок, требующих изменения входных данных или бизнес-решения.
- Повторный запрос должен учитывать возможность выполнения первоначальной операции.
- Тайм-ауты, интервалы между повторами, максимальное число попыток и условия прекращения повторов должны задаваться в соответствующей технической спецификации.
- Если параметры не определены, агент может предложить обоснованные значения как рабочие допущения, но не должен представлять их как подтверждённые требования.

**4.7. Согласованность состояния и результата**
**Правило:** Отображаемый результат операции должен соответствовать последнему достоверно установленному состоянию.
**Следствия:**
- Промежуточное состояние не должно выдаваться за финальное.
- Неопределённый результат должен оставаться различимым от успеха и окончательной ошибки.
- Система должна иметь возможность обновить результат после получения дополнительных сведений от внешней системы.
- Конкретные названия состояний и допустимые переходы определяются в модели состояний.

**4.8. Проверка полномочий инициатора**
**Правило:** Перед выполнением операции система должна проверять, имеет ли инициатор право выполнить её в отношении соответствующего объекта.
**Следствия:**
- Право на выполнение операции должно оцениваться с учётом контекста операции и целевого объекта.
- Получение идентификатора документа, пакета или сертификата само по себе не предоставляет право на выполнение операции.
- Конкретные роли, полномочия и правила авторизации должны определяться требованиями безопасности и бизнес-моделью доступа.

## 5. Правила API и интеграционного взаимодействия

**5.1. Явное описание контрактов**
**Правило:** Для API должны быть явно определены структура запросов, структура ответов и семантика взаимодействия.
**Следствия:**
- Для каждого endpoint необходимо определить назначение, входные данные и возможные результаты.
- При необходимости должны быть описаны ошибки, ограничения, требования к авторизации и правила повторных запросов.
- Неопределённые поля и параметры должны быть помечены как допущения или вопросы, а не молча исключаться из анализа.

**5.2. Разделение внутренних и внешних моделей**
**Правило:** Внутренняя модель сервиса может отличаться от модели данных внешней системы.
**Следствия:**
- Внешние контракты не обязаны полностью повторять внутреннюю структуру данных.
- Преобразования данных должны быть отражены там, где они влияют на поведение системы или интеграцию.
- Ограничения внешнего API не должны автоматически трактоваться как ограничения внутренней модели, если это не следует из требований.

**5.3. Обработка временных ошибок внешних систем**
**Правило:** Ошибки внешних систем должны классифицироваться с учётом возможности временного восстановления.
**Следствия:**
- Для временных ошибок могут предусматриваться повторные попытки.
- Для окончательных ошибок повторение без изменения условий не должно выполняться автоматически, если это не обосновано контрактом.
- Поведение при недоступности внешней системы должно быть описано в соответствующих сценариях.

**5.4 Проверка результата перед повтором операции**
**Правило:** Перед повторением операции с потенциально необратимым эффектом необходимо учитывать возможность того, что предыдущая попытка уже была выполнена.
**Следствия:**
- Если внешний сервис предоставляет способ запросить состояние операции или объекта, этот механизм следует рассматривать как основной способ устранения неопределённости.
- Повторное выполнение без проверки допустимо только при наличии обоснованного безопасного механизма, например гарантированной идемпотентности.
- Если получить достоверный результат невозможно, система должна сохранять неопределённость и предусматривать дальнейшую обработку ситуации.
