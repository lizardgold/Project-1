## 7. Отклонения от правил SHOULD с обоснованием

| № | Правило | Формулировка (кратко) | Обоснование отклонения |
|---|---|---|---|
| 1 | `path-max-nesting-depth` | Не более 4 уровней вложенности пути | Пути `/signing-packages/{packageId}/documents/{documentId}/content` и `.../signatures` имеют 5 сегментов. Уплощение потребовало бы вынести `documentId` в корень и дублировать проверки принадлежности документов пакету, что повышает риск ошибок доступа (BOLA) |
| 2 | `operation-ref-resource-file` | Endpoint должен ссылаться на файл в `resources/` | Проект ведёт спецификацию одним самодостаточным файлом; разбиение на `resources/` не принято и затруднило бы проверку артефакта |
| 3 | `operation-use-ref` | Endpoint должен быть `$ref` | То же: единый файл спецификации без вынесенных path-item |
| 4 | `path-cors-support-options-preflight` | Описать `OPTIONS` для CORS preflight | CORS обслуживается API-шлюзом и не относится к контракту фичи; включение `OPTIONS` расширило бы область DoD |
| 5 | `request-body-must-use-json-content-type` | Тела запросов — `application/json` | Для `PUT .../content` используется `application/pdf`: передача файла в JSON (base64) увеличивает объём на 33 % и исключает потоковую передачу |
| 6 | `request-support-form-urlencoded-media-type` | Поддержка `application/x-www-form-urlencoded` | API принимает JSON и бинарный PDF; формы не предусмотрены сценарием |
| 7 | `request-support-multipart-media-type` | Поддержка `multipart/form-data` | Документы передаются отдельными запросами; многочастная загрузка не требуется |
| 8 | `request-support-text-plain-media-type` | Поддержка `text/plain` | Текстовые тела в контракте не предусмотрены |
| 9 | `request-support-xml-media-type` | Поддержка `application/xml` | Контракт JSON-only по соглашению проекта; XML не используется ни одной стороной |
| 10 | `header-names-hyphenated-pascal-case` | Заголовки — `Hyphenated-Pascal-Case` | `RateLimit-Limit`/`-Remaining`/`-Reset` (IETF RateLimit) и `WWW-Authenticate` (RFC 9110) имеют стандартизованные имена, изменять их нельзя |
| 11 | `operation-get-support-if-modified-since` | Поддержка `If-Modified-Since` | Условные запросы реализованы через `ETag`/`If-None-Match`; `If-Modified-Since` не поддержан |
| 12 | `operation-write-support-if-unmodified-since` | Поддержка `If-Unmodified-Since` | Используется `If-Match` с `ETag` — более точный механизм для конкурентных изменений состояния |
| 13 | `request-header-names-pascal-case` | Заголовки запроса — PascalCase | `traceparent` задан спецификацией W3C Trace Context в нижнем регистре; остальные заголовки требованию соответствуют |
| 14 | `request-support-accept-encoding` | Поддержка `Accept-Encoding` | Сжатие ответов обеспечивается API-шлюзом, а не сервисом |
| 15 | `request-support-accept-language` | Поддержка `Accept-Language` | Локализация не входит в область задачи; язык ответов фиксирован |
| 16 | `request-support-baggage` | Поддержка `baggage` (W3C) | Распространение прикладного контекста не требуется; используется `traceparent` |
| 17 | `request-support-tracestate` | Поддержка `tracestate` | Вендорское состояние трассировки не используется |
| 18 | `license-url` | `license.url` обязателен | Проприетарная лицензия не имеет публичного URL; указан `license.identifier` (допустимо в OpenAPI 3.1) |
| 19 | `info-license-require-url` | URL лицензии в `info` | То же: публичный URL лицензии не определён |
| 20 | `response-require-status-health-check-path` | Наличие `/status` | `/status` относится к платформенному контракту сервиса, а не к сценарию подписания; включение расширило бы границы задачи |

| 23 | `response-ratelimit-header` | Структурированный `RateLimit` (IETF draft) | Используется триплет `RateLimit-Limit`/`-Remaining`/`-Reset`, поддерживаемый шлюзом; политика описана в `x-rate-limits` |
| 24 | `response-ratelimit-policy` | Заголовок `RateLimit-Policy` | Политика квот зафиксирована в `x-rate-limits` и не передаётся заголовком до согласования формата |
| 25 | `response-return-correlation-id` | Возврат идентификатора корреляции | Для ошибок идентификатор возвращается в `Problem.traceId`; в успешных ответах заголовок не объявлен, чтобы не расширять контракт без требования партнёров |

| 27 | `schema-property-no-prepositions` | Без предлогов в именах | Временные метки используют общепринятый суффикс `At` (`createdAt`, `expiresAt`, `signedAt`); предлогов в значении правила в именах нет |
| 28 | `schema-string-require-pattern-or-format` | Шаблон или формат для строк | Свободный текст (`title`, `comment`, `statusReason`, `failureMessage`, `subjectCommonName`, `issuerName`) ограничен длиной; шаблон для него нецелесообразен |
| 29 | `no-$ref-siblings` | Нет полей рядом с `$ref` | OpenAPI 3.1 допускает соседние поля с `$ref`; они используются для описания свойства при ссылке на перечисление |

## 8. Взаимоисключающие правила (19)

По каждому семейству выполнено одно правило; одновременное выполнение невозможно.

| Семейство правил | Выбранное решение | Причина |
|---|---|---|
| `path-include-version` ↔ `path-no-version-segment` | Версия в `servers[].url` (`/v1`), пути без версии | Правила противоречат друг другу; версионирование через базовый URL сохраняет стабильность путей |
| `response-success-use-hal-json` ↔ `response-use-json-api` ↔ `response-must-use-json-content-type` | `application/json` для успешных ответов, `application/problem+json` для ошибок | Три правила требуют разных медиатипов для одних и тех же ответов; выбран наиболее совместимый |
| `response-location-header-only-on-201` ↔ `response-202-location-header` | `Location` в ответах `201` и `202` | `202` обязан содержать ссылку на отслеживаемый ресурс |
| `schema-definition-camel-case` / `-constant-case` / `-kebab-case` / `-snake-case` ↔ `schema-names-pascal-case` | Имена схем — PascalCase | Взаимоисключающие варианты записи имён |
| `schema-keys-snake-case` ↔ `schema-property-camel-case` | Ключи схем — PascalCase, свойства — camelCase | Snake_case ключей схем противоречит правилам camelCase/PascalCase |
| `schema-property-pascal-case` / `-constant-case` / `-kebab-case` / `-snake-case` ↔ `schema-property-camel-case` | Свойства — camelCase | Взаимоисключающие варианты записи |
| `parameter-keys-snake-case` / `path-parameter-*` (4 правила) ↔ `path-parameter-camel-case` | Параметры пути — camelCase | Взаимоисключающие варианты записи |
| `response-keys-snake-case` ↔ `response-names-pascal-case` | Имена компонентов ответов — PascalCase | Snake_case имён ответов противоречит PascalCase |

## 10. Правила, содержащие в формулировке «MUST»

В `linter.md` 252 вхождения слова «MUST» внутри текста правил. Они не являются уровнем
правила (все правила размечены как SHOULD), но выражают обязательность. Проверка выполнена
следующим образом:

- детерминированные обязательные формулировки проверены как обязательные и выполнены:
  `additionalProperties`, семантическое версионирование, `security` на корне,
  `securitySchemes`, обязательные ответы `400`/`401`/`429`/`500`, стандартные HTTP-коды,
  camelCase-имена свойств, `application/json`, HTTPS-серверы;
- противоречивые обязательные формулировки отнесены к взаимоисключающим (раздел 8):
  `application/hal+json` против `application/vnd.api+json` против `application/json`,
  `multipart/form-data` против `application/x-www-form-urlencoded` против JSON,
  версия в пути против запрета версии в пути, `Location` только в `201` против `Location` в `202`.

## 11. Ограничения проверки

1. Локальный `linter.md` содержит текстовые формулировки правил без параметров (порогов длин,
   перечней допустимых значений), поэтому часть правил проверена экспертно, а не машинно.
2. Проверка не выполнялась внешним сервисом API Commons; использованы локальный набор правил
   и перечисленные инструменты.
3. Правила, зависящие от внешней инфраструктуры (CORS, сжатие, локализация, квоты), проверены
   на уровне контракта: соответствующие обязанности отнесены к API-шлюзу.
4. Смысловые правила (полнота бизнес-сценариев, корректность статусов) проверены отдельно —
   трассировкой `x-requirements-traceability` и сверкой с `knowledge/business rules.md`.

## 12. Вывод и рекомендации

**Вывод:** спецификация `OpenAPI-31.10.2026-1.yaml` валидна как OpenAPI 3.1.0, не содержит
нарушений уровня **MUST** и пригодна для передачи в разработку и для генерации клиентского кода.
Нарушений SHOULD, требующих исправления, не осталось; 29 отклонений и 19 взаимоисключающих
правил обоснованы.

**Рекомендации:**

1. При пересмотре URL-схемы рассмотреть уплощение путей документов
   (`/documents/{documentId}/content`, `/documents/{documentId}/signatures`), чтобы выполнить
   `path-max-nesting-depth` без дублирования проверок доступа.
2. Вынести `/status` и CORS-политику в платформенный контракт сервиса и сослаться на него
   из этой спецификации.
3. После подтверждения формата квот перейти на структурированные заголовки `RateLimit`
   и `RateLimit-Policy` (IETF draft) вместо триплета.
4. Уточнить открытые вопросы `x-open-questions` (подтверждение клиента, криптографический
   профиль, лимиты, владелец клиентского токена) до согласования контракта с партнёрами.
